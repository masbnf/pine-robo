دو سؤال کاملاً جدا

پروژه عمداً این دو تصمیم را در دو جای متفاوت نگه می‌دارد:

  1. «چند درصد equity را ریسک کنیم؟» — این تصمیم سیاستی است و داخل PaperBroker._open با یک زنجیرهٔ if/elif روی مدل‌های ریسک تطبیقی BotConfig گرفته می‌شود (بخش بعدی).
  2. «با آن درصد، دقیقاً چند لات؟» — این یک محاسبهٔ ریاضی محض و قطعی است، کاملاً مستقل از هر مدل تطبیقی، در position_sizing.py.

این جداسازی یعنی می‌توانید کل استراتژی انتخاب درصد ریسک را عوض کنید بدون آنکه حتی یک خط از ریاضیات حجم را لمس کنید.

کد: calculate_safe_position_size

pine_ob_bot/position_sizing.py — calculate_safe_position_size (خلاصه‌شده)
def calculate_safe_position_size(equity, risk_percent, entry_price, stop_loss,
                                   tick_size, tick_value,
                                   volume_min, volume_max, volume_step):
    if equity <= 0 or risk_percent <= 0:
        return PositionSizeResult(0, 0, 0, False, INVALID_RISK_INPUT)
    if tick_size <= 0 or tick_value <= 0 or volume_step <= 0 or volume_min <= 0 or volume_max <= 0:
        return PositionSizeResult(0, 0, 0, False, INVALID_SYMBOL_SPEC)

    allowed_risk = equity * risk_percent
    distance = abs(entry_price - stop_loss)
    if distance <= 0:
        return PositionSizeResult(0, allowed_risk, 0, False, INVALID_STOP_DISTANCE)

    loss_per_lot = distance / tick_size * tick_value
    raw_volume = allowed_risk / loss_per_lot
    capped_volume = min(raw_volume, volume_max)
    normalized_volume = floor((capped_volume + _STEP_EPSILON) / volume_step) * volume_step

    if normalized_volume < volume_min - _STEP_EPSILON:
        actual_risk = normalized_volume * loss_per_lot
        return PositionSizeResult(normalized_volume, allowed_risk, actual_risk,
                                   False, CALCULATED_VOLUME_BELOW_BROKER_MINIMUM)

    actual_risk = normalized_volume * loss_per_lot
    if actual_risk > allowed_risk * _RISK_TOLERANCE:
        return PositionSizeResult(normalized_volume, allowed_risk, actual_risk,
                                   False, ACTUAL_RISK_EXCEEDS_ALLOWED_RISK)

    return PositionSizeResult(normalized_volume, allowed_risk, actual_risk, True, None)

خط به خط، نکتهٔ محوری: normalized_volume با floor (نه round، نه ceil) به نزدیک‌ترین مضرب volume_step پایین گرد می‌شود — یعنی حجم محاسبه‌شده هرگز نمی‌تواند از حد ریسک مجاز فراتر برود. اگر بعد از این گرد کردن، حجم هنوز کمتر از volume_min باشد، تابع رد می‌کند، به‌جای اینکه حجم را تا volume_min بالا ببرد — دقیقاً همان «رفتار قدیمی و باگ‌دار» که در تست‌ها صراحتاً به‌عنوان مرجع مقایسه ذکر شده: بالا بردن حجم به حداقل بروکر، یعنی خاموش ریسک کردن بیشتر از آنچه کاربر خواسته — دقیقاً همان چیزی که این تابع برای جلوگیری از آن نوشته شده.

نکته سناریوی رگرسیونی مشخصی که در تست‌ها به‌عنوان انگیزهٔ اصلی این ماژول ذکر شده: equity=۱۰,۰۰۰، ریسک=۱٪، فاصلهٔ Stop=۱۰۰۰ — یک سناریوی واقعی که رفتار اشتباه قدیمی را آشکار می‌کرد.

انتخاب کسر ریسک: زنجیرهٔ مدل‌های تطبیقی

داخل PaperBroker._open، پیش از فراخوانی تابع بالا، یک زنجیرهٔ طولانی if/elif روی شش پرچم متقابلاً انحصاری BotConfig (فصل ۴) عبور می‌کند تا risk_fraction نهایی را انتخاب کند:

مدلمعیار انتخاب کسر
Liquidityآیا setup یک Sweep نقدینگیِ مرتبط داشته؟ (۰/۱ سیگنال)
CHoCHآیا در لحظهٔ پر شدن، یک CHoCH مخالف اخیر رخ داده؟
Combined Contextترکیب Liquidity + CHoCH → امتیاز ۰/۱/۲
Displacementآیا رتبهٔ درصدی قدرت شکست در چارک بالاست؟
CHoCH + Displacementترکیب هر دو (پیش‌فرض ضمنی CLI)
Three-FactorCHoCH + Displacement + سن ورود → امتیاز ۰ تا ۳

روی این، دو override غیرانحصاری اضافه می‌شوند (bos_three_factor_risk_enabled، choch_split_risk_enabled)، سپس یک پاداش جمع‌شدنی برای BOS مخالف M15 (bos_m15_counter_bonus_fraction، سقف ۱.۲۵٪)، و در پایان اگر setup از نوع CHoCH باشد و choch_risk_cap_fraction تنظیم شده باشد، کسر نهایی با یک سقف حداکثری min(...) محدود می‌شود.

آزمایشگاه تعاملی: محاسبهٔ Risk Sizing

بخش واقعی پروژه: pine_ob_bot/position_sizing.py → تابع calculate_safe_position_size. این آزمایش فقط لایهٔ ریاضی حجم را نشان می‌دهد؛ زنجیرهٔ انتخاب درصد ریسک (بالا) موضوع بخشی جداست که هنوز آزمایش تعاملی اختصاصی ندارد.

مفاهیم برنامه‌نویسی این فصل

Floor به‌جای Round: انتخاب جهت گرد کردن، وقتی «هرگز فراتر نرو» یک قید سخت است، خودش یک تصمیم طراحی حیاتی است — round() می‌توانست نیمی از مواقع حجم را بالا ببرد و ریسک واقعی را از حد مجاز رد کند.

Epsilon برای خطای اعشاری: _STEP_EPSILON = 1e-9 فقط برای خنثی کردن خطای گرد کردن ذاتی اعداد اعشاری (floating point) استفاده می‌شود، هرگز برای توجیه ریسک اضافه — نکته‌ای مهم در هر محاسبهٔ مالی با اعداد اعشاری.

رد به‌جای گرد کردن اجباری (Fail-safe over Silent Correction): وقتی سیستم نمی‌تواند قید ایمنی را برآورده کند، به‌جای «تلاش برای درست کردن» (که می‌تواند ریسک پنهان اضافه کند)، آشکارا رد می‌کند و دلیل را گزارش می‌دهد.

اشتباهات رایج

  • فرض اینکه رد شدن به‌خاطر CALCULATED_VOLUME_BELOW_BROKER_MINIMUM یک باگ است — این رفتار عمدی و درست است؛ نمونهٔ باگ قدیمی دقیقاً برعکسش بود.
  • خلط دو تصمیم «چند درصد» و «چند لات» با هم و تلاش برای تغییر همزمان آن‌ها در یک نقطه از کد.
  • فراموش کردن اینکه شش مدل تطبیقی متقابلاً انحصاری‌اند — نمی‌توان بیش از یکی را هم‌زمان روشن کرد (فصل ۴، validate()).

تمرین عملی

تمرین (متوسط)

در آزمایشگاه بالا، مقادیر equity=۱۰۰۰۰، ریسک=۱٪، entry=۲۰۰۰، stop=۱۹۰۰ (فاصلهٔ ۱۰۰) را وارد کنید. حجم محاسبه‌شده را با فرمول دستی allowed_risk / (distance/tick_size*tick_value) مقایسه کنید، سپس volume_step را طوری تغییر دهید که خروجی به زیر volume_min برود و ببینید پیام رد چیست.

راهنما

برای رساندن حجم زیر حداقل، یا equity را خیلی کم کنید یا فاصلهٔ Stop را خیلی زیاد.

خلاصهٔ فصل

calculate_safe_position_size یک تابع خالص، قطعی و به‌شدت تست‌شده است که هرگز اجازه نمی‌دهد ریسک واقعی از ریسک مجاز فراتر برود — با ترجیح رد آشکار بر گرد کردن پنهان. کدام درصد ریسک به این تابع داده می‌شود، تصمیمی کاملاً جداست که در یک زنجیرهٔ مدل‌های تطبیقی داخل PaperBroker._open گرفته می‌شود.
