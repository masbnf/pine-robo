مفاهیم برنامه‌نویسی: dataclass، type hint، Literal

Type hint: نوشتن open: float به‌جای فقط open مستندسازی زنده است — هم برای انسان (این فیلد عدد اعشاری است) و هم برای ابزارهایی مثل type checker/IDE. پایتون خودش این را در زمان اجرا اجباری نمی‌کند، اما در این پروژه نظم زیادی به کد می‌دهد.

Literal["bull", "bear"]: به‌جای اینکه جهت معامله یک رشتهٔ آزاد باشد، Direction = Literal["bull", "bear"] فقط همین دو مقدار دقیق را مجاز می‌داند — یک type checker می‌تواند typo مثل "buy" به‌جای "bull" را پیش از اجرا پیدا کند.

Computed property روی dataclass: بعضی مدل‌ها (مثل OrderBlock) علاوه بر فیلدهای خام، متدهایی با @property دارند که از همان فیلدها مقدار جدیدی محاسبه می‌کنند — بدون اینکه آن مقدار را دوباره ذخیره کنند (پرهیز از دادهٔ تکراری/ناسازگار).

هشت مدل داده

Candle

فیلدها: time: str (ISO-8601)، open، high، low، close: float. یک کندل بستهٔ M5 (یا M15 تجمیع‌شده).

Tick

فیلدها: time: str، bid: float، ask: float. یک نقل‌قول زنده/بازپخش‌شده.

Pivot

فیلدها: level: float، bar_index: int، time: str، crossed: bool = False. یک Swing High/Low تأییدشدهٔ Trend داخل PineSwingOBEngine؛ crossed نشان می‌دهد آیا قیمت از قبل از آن عبور کرده یا نه (دقیقاً یک‌بار برای یک BOS/CHoCH مصرف می‌شود).

StructureBreak

فیلدها: direction: Direction، kind: Literal["BOS","CHoCH"]، pivot_level، bar_index، time. یک رویداد شکست ساختار که PineSwingOBEngine.process تولید می‌کند.

OrderBlock

فیلدها: id، direction، high، low، source_index، source_time، formed_index، formed_time، active: bool = True، break_kind: str = "unknown"، atr_at_formation: float | None = None.

دو property محاسبه‌شده: entry (اگر bull باشد high، وگرنه low — لبهٔ قابل‌معامله) و stop (برعکس entry — لبهٔ ابطال).

PendingOrder

فیلدها: id، ob_id، direction، entry، stop، target: float، created_index، created_time، active: bool = True، meta: dict (پیش‌فرض کارخانه‌ای)، lifecycle_state: str = "formed"، accepted_index، armed_index: int | None. سفارش محدودِ هنوز پر‌نشده — چرخهٔ کامل عمرش در فصل ۱۳.

PaperPosition

فیلدها: id، order_id، direction، entry، stop، target، volume، risk_money، opened_time، opened_index، max_adverse: float = 0.0، max_favorable: float = 0.0، meta: dict. یک معاملهٔ کاغذیِ باز؛ max_adverse/max_favorable جابه‌جایی خام قیمت هستند (هنوز به R تبدیل نشده‌اند — این تبدیل هنگام بسته‌شدن رخ می‌دهد).

Trade

فیلدها: id، direction، entry، stop، target، exit_price، volume، risk_money، pnl، r_multiple، opened_time، closed_time، result: Literal["win","loss"]، order_id، ob_id، opened_index، closed_index، max_adverse_r، max_favorable_r، meta. رکورد یک معاملهٔ بسته‌شده — واحد خروجی همهٔ گزارش‌ها.

to_dict(value) -> dict

پوششی نازک روی dataclasses.asdict. اغلب ماژول‌ها مستقیم خودِ asdict را صدا می‌زنند، نه این تابع کمکی.

نکته هیچ‌کدام از این کلاس‌ها خودشان فیلدهایشان را اعتبارسنجی نمی‌کنند (مثلاً بررسی high >= low داخل خودِ OrderBlock وجود ندارد) — این کار در محل فراخوانی انجام می‌شود، مثلاً PaperBroker.add_ob که ob.high <= ob.low را قبل از پذیرش بررسی می‌کند.

نمونهٔ کد و توضیح خط‌به‌خط: OrderBlock

pine_ob_bot/models.py — OrderBlock (خلاصه‌شده)
@dataclass(slots=True)
class OrderBlock:
    id: str
    direction: Direction
    high: float
    low: float
    source_index: int
    source_time: str
    formed_index: int
    formed_time: str
    active: bool = True
    break_kind: str = "unknown"
    atr_at_formation: float | None = None

    @property
    def entry(self) -> float:
        return self.high if self.direction == "bull" else self.low

    @property
    def stop(self) -> float:
        return self.low if self.direction == "bull" else self.high

خط به خط: فیلدهای بدون مقدار پیش‌فرض (id تا formed_time) باید هنگام ساخت شیء پاس داده شوند؛ فیلدهای دارای مقدار پیش‌فرض (active به بعد) اختیاری‌اند. entry و stop هیچ فیلد ذخیره‌شده‌ای ندارند — هر بار که خوانده شوند، از روی direction/high/low فعلی محاسبه می‌شوند. این یعنی اگر high یا low بعداً تغییر کند (که در این کلاس رخ نمی‌دهد، اما اصل کلی درست است)، entry/stop همیشه به‌روز می‌مانند — بدون خطر ناسازگاری بین یک مقدار خام و یک مقدار مشتق‌شدهٔ کش‌شده.

آزمایشگاه تعاملی: ساخت Candle

هدف آموزشی: دیدن اینکه چگونه چهار عدد خام (Open/High/Low/Close) به یک شیء واقعیِ Candle پروژه تبدیل می‌شود، و مفاهیم مشتق‌شدهٔ ساده (اندازهٔ range، صعودی/نزولی بودن، اعتبار منطقی OHLC) روی همان شیء چگونه محاسبه می‌شوند.
بخش واقعی پروژه: pine_ob_bot/models.py → کلاس Candle. این نسخهٔ آموزشی، بعد از ساخت شیء Candle واقعی، فقط چند محاسبهٔ کمکی (range، bullish/bearish، اعتبار OHLC) روی آن اضافه می‌کند که خودِ models.py ندارد — چون این پروژه اعتبارسنجی OHLC را در محل مصرف انجام می‌دهد، نه داخل خودِ Candle.

اشتباهات رایج

  • فرض اینکه OrderBlock.entry یک فیلد ذخیره‌شده است — یک property محاسبه‌شده است، هر بار از نو حساب می‌شود.
  • ساختن Candle با high < low و انتظار خطا — خودِ Candle هیچ بررسی‌ای نمی‌کند؛ این مسئولیت کد فراخواننده است.
  • گیج‌شدن بین PaperPosition.max_adverse (قیمت خام) و Trade.max_adverse_r (نرمال‌شده به R) — دو واحد اندازه‌گیری متفاوت‌اند.

نکات طراحی

جداسازیِ «سفارش معلق» (PendingOrder)، «پوزیشن باز» (PaperPosition) و «معاملهٔ بسته» (Trade) به‌جای یک کلاس بزرگ با فیلدهای Optional زیاد، یک تصمیم طراحی آگاهانه است: هر مرحله از عمر یک معامله دقیقاً همان فیلدهایی را دارد که در آن مرحله معنا دارند، نه بیشتر.

تمرین عملی

تمرین (ساده)

در آزمایشگاه بالا، مقادیری وارد کنید که open بیرون از بازهٔ [low, high] باشد. آیا خطا می‌گیرید؟ چرا این رفتار با طراحی models.py سازگار است؟

راهنما

به بخش «نکته» بالا دربارهٔ نبودِ اعتبارسنجی داخل خودِ Candle/OrderBlock برگردید.

پرسش‌های مرور فصل

  1. Direction با Literal چه فایده‌ای نسبت به یک str ساده دارد؟
  2. فرق PaperPosition و Trade چیست و چرا یک کلاس واحد نیستند؟
  3. OrderBlock.entry برای یک OB با direction="bear" کدام فیلد را برمی‌گرداند؟

خلاصهٔ فصل

هشت dataclass ساده و بدون رفتار پیچیده، ستون فقرات دادهٔ کل پروژه‌اند. اعتبارسنجی عمداً از خودِ این کلاس‌ها بیرون نگه داشته شده و به محل مصرف (عمدتاً PaperBroker) واگذار شده است.
