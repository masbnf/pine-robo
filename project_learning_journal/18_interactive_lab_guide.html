هدف فصل

فصل‌های ۵ تا ۱۵ در چند نقطه یک بخش «آزمایشگاه تعاملی» داشتند بدون اینکه توضیح دهند خودِ آن زیرساخت چگونه کار می‌کند. این فصل آن خلأ را پر می‌کند: کد پشتِ صحنه، مسیر یک درخواست از کلیک دکمهٔ «اجرا» در مرورگر تا فراخوانی واقعیِ یک تابع در pine_ob_bot و بازگشتِ نتیجه.

اجرا

پس از اجرا، آدرسی مثل http://127.0.0.1:8766/00_index.html چاپ و (مگر با --no-browser) به‌طور خودکار در مرورگر باز می‌شود. اگر پورت پیش‌فرض اشغال باشد، find_open_port تا ۲۰ پورت بعدی را امتحان می‌کند و پورت واقعی استفاده‌شده را چاپ می‌کند. از این لحظه، تمام صفحات HTML همین پوشه از طریق همین سرور سرو می‌شوند و دکمهٔ «اجرا» در هر آزمایشگاه به یک درخواست واقعی POST /api/run متصل می‌شود.

حالت بدون سرور

اگر فایل‌های HTML را مستقیماً (با دابل‌کلیک یا file://) بدون اجرای serve_journal.py باز کنید، متن، کد، جدول‌ها و نمودارها کامل قابل خواندن‌اند — فقط بخش آزمایشگاه، به‌جای خروجی زنده، پیام «برای اجرای تعاملی، serve_journal.py را اجرا کنید» را نشان می‌دهد (این رفتار در lab-client.js پیاده شده: وقتی fetch("./api/run") شکست بخورد — چه به‌خاطر نبودِ سرور، چه به‌خاطر باز بودن از file:// — به‌جای صفحهٔ خراب یا سفید، همین پیام راهنما نمایش داده می‌شود).

معماری کلی

آزمایشگاه از سه لایهٔ مستقل تشکیل شده که هرکدام مسئولیت محدودی دارد:

  • Frontend (lab-client.js): یک تابع عمومی JournalLab.mount(config) که از روی یک شیء تنظیمات اعلانی (فیلدها، برچسب فارسی، نوع، بازهٔ مجاز)، فرم HTML را می‌سازد، پیش از ارسال روی خودِ مرورگر اعتبارسنجی سبک انجام می‌دهد، و نتیجه را در چند سطح (خلاصه، مراحل، معیارها، JSON خام) نمایش می‌دهد.
  • HTTP Server (serve_journal.py): یک ThreadingHTTPServer مبتنی بر کتابخانهٔ استاندارد پایتون. GET فقط فایل‌های همین پوشه را سرو می‌کند؛ POST فقط مسیر دقیق /api/run را می‌پذیرد.
  • Experiment Registry (lab_experiments.py): رجیستری EXPERIMENTS که هر شناسهٔ آزمایش را به یک تابع handler و یک لیست فیلد مجاز نگاشت می‌کند؛ هر handler کد واقعی pine_ob_bot را import و اجرا می‌کند.

نکتهٔ مهم مسیر داده: فرانت‌اند هرگز نام تابع یا کد پایتون نمی‌فرستد — فقط یک experiment_id رشته‌ای (مثلاً "risk_sizing_calculator") و یک شیء inputs. بک‌اند این شناسه را در EXPERIMENTS جست‌وجو می‌کند؛ اگر پیدا نشود، هیچ کدی اجرا نمی‌شود.

نمودار: مسیر یک درخواست آزمایش

فرانت‌اند فقط experiment_id و مقادیر ورودی می‌فرستد؛ سرور شناسه را در رجیستری ثابت جست‌وجو می‌کند، ورودی‌ها را با schema اعتبارسنجی می‌کند، و تنها در صورت عبور از هر دو ایست، handلر واقعی — که کد اصلی pine_ob_bot را صدا می‌زند — اجرا می‌شود.

معماری امنیتی

این آزمایشگاه اجازهٔ اجرای کد دلخواه کاربر را نمی‌دهد — نه eval، نه exec، نه subprocess/os.system، نه import پویا، نه مسیر فایل دلخواه، نه اتصال شبکه/MT5، نه ارسال سفارش. هر آزمایش از قبل، به‌عنوان یک تابع پایتونی ثابت در lab_experiments.py، نوشته شده؛ کاربر فقط اجازه دارد مقدار چند ورودی از پیش‌تعریف‌شده را تغییر دهد، نه خودِ منطق.

pine_ob_bot/…/serve_journal.py — JournalRequestHandler._safe_static_path
def _safe_static_path(self, url_path: str) -> Path | None:
    if url_path in ("", "/"):
        url_path = "/00_index.html"
    rel = url_path.lstrip("/")
    candidate = (JOURNAL_ROOT / rel).resolve()
    try:
        candidate.relative_to(JOURNAL_ROOT)
    except ValueError:
        return None  # تلاش برای path traversal
    if candidate.name.startswith("_") or "runtime_data" in candidate.parts:
        return None  # فایل‌های داخلی/کاری، هرگز سرو نشوند
    if not candidate.exists() or not candidate.is_file():
        return None
    return candidate

خط به خط: (JOURNAL_ROOT / rel).resolve() مسیر را به شکل مطلق و نرمال‌شده تبدیل می‌کند (شامل حل کردن ..)؛ سپس candidate.relative_to(JOURNAL_ROOT) تضمین می‌کند که مسیر نهایی هنوز داخل همین پوشه است — اگر کاربر مثلاً /../../etc/passwd بفرستد، relative_to یک ValueError پرتاب می‌کند و تابع None برمی‌گرداند (که در do_GET به ۴۰۴ تبدیل می‌شود، نه خطای سرور). خط بعد صریحاً فایل‌های داخلی (شروع‌شونده با _، مثل lab_experiments.py اگر کسی حدس بزند) و هر چیز داخل runtime_data/ را مسدود می‌کند — یعنی حتی فایل‌های پایتونی سرور هم از طریق HTTP قابل دانلود نیستند.

برای POST /api/run، مسیر امنیتی متفاوت اما به همان اندازه محدودکننده است: تنها ورودی که از کاربر پذیرفته می‌شود یک شناسهٔ رشته‌ای (experiment_id) و یک شیء inputs است. مسیر بین این‌جا تا اجرای واقعی از سه ایست بازرسی عبور می‌کند — وجود شناسه در رجیستری، اعتبارسنجی schema هر فیلد، و اجرای handler درون ThreadPoolExecutor با timeout سخت — که در دو بخش بعدی جداگانه شرح داده شده‌اند.

نکته هیچ‌جای این دو فایل، رشتهٔ ورودی کاربر مستقیماً به یک نام تابع/ماژول یا مسیر فایل تبدیل نمی‌شود. تنها «انتخاب» واقعی کاربر، یک کلید در دیکشنری ثابت EXPERIMENTS است که از پیش در کد سرور نوشته شده — نه چیزی که کاربر بتواند به آن اضافه کند.

اعتبارسنجی ورودی

اعتبارسنجی سمت سرور همیشه مرجع نهایی است (اعتبارسنجی مرورگر فقط برای تجربهٔ کاربری سریع‌تر است و هرگز به‌تنهایی کافی فرض نمی‌شود). تابع validate_inputs سه کار انجام می‌دهد:

(۳) هر کلید در inputs که در لیست فیلدهای مجاز آن آزمایش نباشد، کل درخواست را رد می‌کند — یعنی حتی اگر بقیهٔ فیلدها معتبر باشند، وجود یک کلید اضافی (که می‌تواند تلاش برای تزریق باشد) کافی است. سپس _validate_scalar هر فیلد را برحسب type اعلان‌شده‌اش (int/float/bool/select/str) و min/max/options بررسی می‌کند.

قرارداد JSON خروجی

هر پاسخ موفق /api/run این شکل را دارد:

{
  "success": true,
  "experiment_id": "risk_sizing_calculator",
  "inputs": { ... ورودی‌های پاک‌سازی‌شده ... },
  "result": { "summary": "...", ... },
  "steps": ["۱. ...", "۲. ...", ...],
  "metrics": { ... },
  "warnings": [],
  "execution_time_ms": 4.2
}

فیلد steps («مراحل اجرا») همیشه از روی مقادیر واقعیِ محاسبه‌شده در طول اجرای handler ساخته می‌شود — نه یک متن ثابت. برای نمونه در h_entry_pivot_detection، خودِ حلقهٔ پردازش کندل‌به‌کندل، هر بار که detector واقعی یک Pivot تأیید می‌کند، یک خط توضیحی به steps اضافه می‌کند؛ اگر پارامترهای ورودی را عوض کنید، متن این مراحل هم واقعاً عوض می‌شود چون از خروجی واقعیِ ClassicEntryPivotDetector.process می‌آید.

فیلد result در چند سطح در frontend نمایش داده می‌شود: یک خلاصهٔ یک‌خطی برای مبتدی (result.summary)، مراحل اجرا، معیارهای عددی کلیدی (metrics)، و در یک بخش بازشوندهٔ جداگانه، کل شیء JSON خام برای کسی که می‌خواهد ساختار کامل را ببیند.

کجا از نسخهٔ آموزشی ساده‌شده استفاده شده

اکثر handlerها مستقیماً کلاس‌ها/توابع واقعی pine_ob_bot را فراخوانی می‌کنند (BotConfig، PineSwingOBEngine، ClassicEntryPivotDetector، PaperBroker، calculate_safe_position_size، run_historical). دو استثنای صریح:

قابلیت آزمایشی در h_sweep_and_reclaim، قیمت پر شدن با فرض spread=0 محاسبه می‌شود («نسخهٔ ساده‌شدهٔ آموزشی» — طبق کد واقعی در historical.py/paper.py، برای خرید close + spread و برای فروش close استفاده می‌شود). تابع تعیین‌کنندهٔ خودِ Sweep/Reclaim (PaperBroker._sweep_reclaim_window) اما بدون تغییر و مستقیماً فراخوانی می‌شود.
نکته در h_bos_choch_classifier، خطِ طبقه‌بندی BOS/CHoCH («مخالفِ Trend فعلی = CHoCH، هم‌جهت یا خنثی = BOS») به‌صورت مستقیم در فایل آزمایشگاه هم نوشته شده تا مرحلهٔ آموزشی جدا از فراخوانی PaperBroker.add_ob نمایش داده شود؛ این همان قاعدهٔ یک‌خطیِ pine_engine.py::process است، نه بازنویسی منطق پیچیده‌تر — سپس نتیجهٔ واقعیِ پذیرش/رد همچنان از فراخوانی واقعی add_ob می‌آید، نه از حدس دستی.

جداسازی از ربات واقعی

هیچ handler ای مسیر live (app.py، mt5_feed.py، demo_executor.py، dashboard_server.py) را import یا اجرا نمی‌کند. تنها آزمایشی که فایل روی دیسک می‌نویسد mini_backtest است؛ آن هم یک پوشهٔ موقتِ یکتا (runtime_data/lab_backtest_<uuid>/) می‌سازد، مسیر پایگاه‌دادهٔ BotConfig.db_path را به همان پوشه می‌دهد (نه به دیتابیس اصلی پروژه)، و در پایان با shutil.rmtree(tmp_dir, ignore_errors=True) — چه اجرا موفق شود چه با خطا مواجه شود (بخش finally) — پاک می‌شود.

رفتار نیازمند بررسی در محیط آزمایش این ژورنال (sandbox لینوکسی با یک درایو شبکه‌ای مانت‌شده)، فعال‌سازی PRAGMA journal_mode=WAL در StateStore.__init__ (فایل pine_ob_bot/storage.py) با خطای سطح فایل‌سیستم مواجه شد، چون WAL به قابلیت mmap/حافظهٔ مشترک نیاز دارد که آن فایل‌سیستم خاص فراهم نمی‌کند. این با تست مستقیم sqlite3 (بدون هیچ کد پروژه) روی همان مسیر تکرار و تأیید شد که مخصوص آن محیط sandbox است، نه یک ایراد در کد پروژه یا در lab_experiments.py — روی دیسک محلی واقعی (مثل کامپیوتر شما) انتظار می‌رود mini_backtest بدون مشکل اجرا شود. جزئیات کامل در documentation_report.html.

مفاهیم برنامه‌نویسی این فصل

سرور HTTP حداقلی با کتابخانهٔ استاندارد: بدون هیچ فریم‌ورک خارجی (Flask/FastAPI)، فقط http.server.BaseHTTPRequestHandler و ThreadingHTTPServer — نشان می‌دهد یک API کوچک و امن چقدر کد کم نیاز دارد وقتی محدودهٔ کارش دقیقاً مشخص باشد.

Allowlist در برابر Denylist: رجیستری EXPERIMENTS و لیست فیلدهای مجاز هر آزمایش، هر دو الگوی «فقط چیزی که صریحاً مجاز شده، اجرا می‌شود» را نشان می‌دهند — نه تلاش برای فهرست‌کردن همهٔ چیزهای ممنوع (که همیشه ناقص است).

جداسازی state با پوشهٔ موقتِ یکتا: uuid.uuid4().hex[:12] در h_mini_backtest تضمین می‌کند دو اجرای هم‌زمان هرگز در یک پوشه با هم تداخل نکنند — یک الگوی عمومی برای هر عملیاتی که باید فایل موقت بنویسد.

اشتباهات رایج

  • فرض اینکه چون اعتبارسنجی سمت مرورگر (validateField) رد می‌کند، سمت سرور لازم نیست — سمت سرور همیشه تکرار می‌شود چون مرورگر قابل‌اعتماد نیست.
  • افزودن یک آزمایش جدید بدون افزودن آن به EXPERIMENTS — handler تنها با import شدنش اجرا نمی‌شود، باید در رجیستری هم ثبت شود.
  • نوشتن مستقیم در runtime_data/ با نام فایل ثابت به‌جای یک پوشهٔ موقتِ یکتا — باعث تداخل بین اجراهای هم‌زمان می‌شود.

تمرین عملی

تمرین (متوسط) — یک آزمایش جدید بسازید

یک تابع h_ob_width_atr(inputs) بنویسید که عرض یک Order Block (بر حسب high - low) را به ATR تقسیم می‌کند و نشان می‌دهد آیا از یک آستانهٔ ورودی بزرگ‌تر است یا نه (پیوند با تمرین ۲.۱ فصل ۱۹). سپس آن را در EXPERIMENTS با یک لیست فیلد مناسب (ob_high، ob_low، atr، min_ratio) ثبت کنید.

راهنما

به الگوی h_take_profit_calculator نگاه کنید — کوتاه‌ترین handler موجود، بدون وابستگی به یک broker کامل، نمونهٔ خوبی برای شروع است.

پرسش‌های مرور فصل

  1. چرا فرانت‌اند هرگز نام تابع پایتون نمی‌فرستد، فقط یک experiment_id رشته‌ای؟
  2. اگر یک کلید اضافی و ناشناخته در inputs بفرستید، دقیقاً کدام تابع و کدام خط آن را رد می‌کند؟
  3. چرا mini_backtest تنها آزمایشی است که به یک پوشهٔ موقتِ یکتا نیاز دارد، در حالی که بقیه ندارند؟

خلاصهٔ فصل

آزمایشگاه تعاملی از سه لایهٔ ساده تشکیل شده — فرم اعلانی در مرورگر، یک سرور HTTP حداقلی، و رجیستری‌ای از توابع از پیش‌نوشته‌شده که مستقیماً کد واقعی pine_ob_bot را اجرا می‌کنند. هیچ کد دلخواهی از کاربر پذیرفته نمی‌شود؛ تنها چیزی که کاربر کنترل می‌کند، مقدار چند ورودی عددی/انتخابیِ از پیش تعریف‌شده است.
