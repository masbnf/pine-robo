چرا یک Pivot دوم و جدا؟

Trend Swing (فصل ۶) با یک پنجرهٔ متقارن (چپ = راست = trend_swing_length) کار می‌کند و هدفش تشخیص ساختار بزرگ بازار است. Entry Pivot اما یک detector کلاسیک و کاملاً مستقل است، با پنجره‌های نامتقارن مجاز (entry_pivot_left، entry_pivot_right، پیش‌فرض هر دو ۵) و هدفش فقط این است: «آخرین نقطهٔ برگشت محلی قیمت کجا بود، تا زمان‌بندی ورود روی یک Order Block از قبل تأیید‌شده را بهتر تنظیم کنیم».

این دو Pivot detector هیچ‌گاه با هم صحبت نمی‌کنند — ClassicEntryPivotDetector هرگز current_m5_trend را نمی‌خواند یا تغییر نمی‌دهد.

کد: ClassicEntryPivotDetector.process

pine_ob_bot/entry_pivot.py — ClassicEntryPivotDetector.process (خلاصه‌شده)
def process(self, candle: Candle) -> list[EntryPivot]:
    self.candles.append(candle)
    local_i = len(self.candles) - 1
    candidate_local = local_i - self.right_bars
    if candidate_local < self.left_bars:
        return []  # هنوز کندل چپ کافی نیست

    left = self.candles[candidate_local - self.left_bars: candidate_local]
    right = self.candles[candidate_local + 1: candidate_local + 1 + self.right_bars]
    candidate = self.candles[candidate_local]

    found = []
    if all(candidate.high > c.high for c in left + right):
        found.append(EntryPivot(kind=PIVOT_HIGH, price=candidate.high, ...))
    if all(candidate.low < c.low for c in left + right):
        found.append(EntryPivot(kind=PIVOT_LOW, price=candidate.low, ...))
    return found

خط به خط: candidate_local = local_i - right_bars یعنی کاندیدای Pivot همیشه right_bars کندل عقب‌تر از کندل تازه‌رسیده است — این «پنجرهٔ راست» همان تأخیر تأییدی است که باید صبرش کنیم. شرط all(candidate.high > c.high ...) از نامساوی اکید استفاده می‌کند (> نه >=) — یعنی تساوی هرگز به‌عنوان Pivot شمرده نمی‌شود. توجه کنید یک کندل واحد می‌تواند هم‌زمان هم Pivot High و هم Pivot Low باشد (دو if جدا، نه elif).

نکته — تأییدشده با تست test_entry_pivot_freshness.py صریحاً تأیید می‌کند که اندازهٔ پنجرهٔ چپ (left_bars) هیچ اثری روی تأخیر تأیید ندارد — فقط right_bars تعیین می‌کند «چند کندل باید صبر کنیم». پنجرهٔ چپ فقط مشخص می‌کند «کاندیدا باید از چند کندل قبل خودش هم بالاتر/پایین‌تر باشد»، نه اینکه چقدر باید منتظرش بمانیم.

تازگی (Freshness) و سن Pivot

هر EntryPivot دو زمان دارد: pivot_time (زمان خودِ کندل کاندیدا — هرگز نباید برای تصمیم معاملاتی استفاده شود، چون در آن لحظه هنوز تأیید نشده بود) و confirmed_at (زمان کندلی که پنجرهٔ راست را بست — این همان چیزی است که منطق معاملاتی باید از آن استفاده کند). در فصل ۱۰ می‌بینیم PaperBroker.add_ob چگونه سن یک Pivot (بر حسب کندل، از لحظهٔ تأیید تا لحظهٔ فرم‌شدن Order Block) را محاسبه و در برابر cfg.max_entry_pivot_age_bars بررسی می‌کند — یک Pivot خیلی قدیمی «Stale» شمرده و رد می‌شود.

مفاهیم برنامه‌نویسی این فصل

Frozen dataclass: EntryPivot با @dataclass(frozen=True, slots=True) تعریف شده — یعنی بعد از ساخته‌شدن، هیچ فیلدش قابل تغییر نیست. این برای یک رویداد تاریخی (چیزی که در گذشته اتفاق افتاده و دیگر نباید عوض شود) انتخاب طبیعی است، برخلاف PendingOrder که عمداً قابل‌تغییر است چون در طول زمان state عوض می‌کند.

بافر لغزان با offset: self.index_offset اجازه می‌دهد بافر self.candles از زمان به زمان کوتاه (trim) شود بدون آنکه اندیس‌های قبلاً منتشرشده بی‌معنا شوند — الگویی رایج برای نگه‌داشتن فقط تاریخچهٔ لازم در برنامه‌های طولانی‌مدت.

اشتباهات رایج

  • استفاده از pivot_time به‌جای confirmed_at برای هر تصمیم زمان‌بندی — این «نگاه به آینده» (look-ahead) است و در بک‌تست واقعی هرگز در آن لحظه در دسترس نبود.
  • تصور اینکه Entry Pivot می‌تواند جهت Trend را عوض کند — نمی‌تواند؛ کاملاً مشاهده‌گر و مستقل است.
  • گمان اینکه پنجرهٔ چپ بزرگ‌تر یعنی تأخیر تأیید بیشتر — طبق تست پروژه این‌طور نیست.
